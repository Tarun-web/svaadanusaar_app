# Nutrition Engine - read-only PostgreSQL preflight

`nutrition_engine_preflight.sql` is a diagnostic pack for the **existing** (hybrid Flyway/Hibernate) database.
It contains 50 statements. Every one is a `SELECT` or `WITH ... SELECT`.

**Status: written and statically checked only. It has not been run against any PostgreSQL server.**
A syntax error is a defect in the pack, not a finding about the database.

## Safety properties

- No `INSERT`, `UPDATE`, `DELETE`, `ALTER`, `DROP`, `CREATE`, `SET`, `BEGIN`/`COMMIT` or `DO` statements.
  A lint pass confirmed that none of those keywords appears outside comments and string literals.
- Row counts use `query_to_xml('select count(*) ...')`. That executes a generated read-only `SELECT`.
- No user rows are returned. The only data values are:
  - the Flyway history (`installed_by` is a database role name);
  - at most 10 distinct unexpected enum strings per column in S5.6 (enum names, not personal data).
- No credentials are read or printed. The pack never touches connection settings.
- Run it on a read-only role or a read-only session, one statement at a time, and keep every result.
  `search_path` must include `public`.

## Run order and how to read it

Every result starts with a section tag. Run S0, then S1, and so on. `[CONDITIONAL]` statements fail with
`relation ... does not exist` when their table is missing. That error is itself a finding, so record it.
Take S6.1 (the gate table) last, as the summary.

### Mandatory stop after S1.1

S1.2 and every later Flyway-history statement (S1.3, S1.3b, S1.3c, S1.4, S1.5, S1.6 and the history joins in S1.7)
read `flyway_schema_history` **unqualified**, so they resolve it through the current `search_path`. They do not
look in `public` specifically, and the pack never assumes the history table is there.

**Stop before S1.2 and do not run any of those statements if either of these is true:**

- S1.1 returns **no row**. The history table is not visible to this role.
  It may not exist, or it may exist in a schema this role cannot see.
- S1.1 returns a row whose `schema_name` is **not `public`**, or returns more than one row.
  The history table is outside `public`, and the unqualified statements may read the wrong table or fail.
- S1.1 returns a row in `public`, but the `search_path` reported by S0.1 does not include `public`.
  S1.1 searches every schema, whereas the unqualified statements resolve only through `search_path`, so they
  would fail or read a different table.

In each case, record the S1.1 result and resolve it before continuing. For example, find out which schema Flyway
is configured to use. Do not edit the pack to point at a guessed schema, and do not treat the later S1 results
as evidence about the Flyway history. The remaining sections (S0, S2 to S5) do not depend on S1.1 and may still
be run, but S6.1 gates G01 and G02 are not meaningful until the history table is located. Those two gates look
only at `public.flyway_schema_history`, so they report a failure when the table lives elsewhere.

## The V17 question (S1.4, S1.5, S1.7, S1.8, S1.9)

V3 creates `allergies text[]`. V17 runs `ADD COLUMN allergies JSONB` with no `IF NOT EXISTS`. Both cannot succeed on one table.
The git history is clean: one commit each, no later edits, no divergent branch. So an edited file is not the explanation.
The sections read together give one verdict:

| Observation | Meaning |
|---|---|
| S1.8 `allergies` is `ARRAY`, S1.2 shows V17 `success = true` | Strong evidence that the history was edited or baselined by hand, or the table was reshaped outside Flyway. |
| S1.8 `allergies` is `jsonb`, S1.7 V3 legacy columns all present | V3 was changed or the table was dropped and recreated outside Flyway. |
| S1.4 shows `CHECKSUM_MISMATCH` for V3 or V17 | Someone changed the recorded checksum (`flyway repair`) or edited the file after applying. The git check says the file did not change. |
| S1.2 has no V17 row | V17 never ran here; `allergies` would then be `text[]` and V17's effects absent. |
| S1.6/S1.5 show a backwards timestamp, or V17 earlier than V3 | History edited by hand. |
| S1.10 has `dropped_columns > 0` | The table was altered and columns removed (consistent with manual changes). |
| S1.9 shows an old legacy table with rows | V17's DROP never ran against this data. |

This pack provides evidence only. It cannot say who changed what.

## Gates: what blocks V100

`passed = false` on a **BLOCKER** gate means do not design V100 yet. **WARNING** means it needs a decision. **INFO** is context.

| Gate | Blocks V100? | Why |
|---|---|---|
| G01 Flyway history exists; G02 no failed rows | **Yes** | The database is not cleanly Flyway-managed. |
| G03 `health_profiles` exists | **Yes** | Nothing else is meaningful. |
| G04 `id` exists; G05 `id` is PK or UNIQUE | **Yes** | V3 shape. The V31 FK and every profile FK need `health_profiles(id)`. |
| G07 `health_profiles.version`; G08 `users.version` | **Yes** | Every UPDATE fails without them. |
| G09 `user_id` unique | **Yes** | The one-profile-per-user guarantee. |
| G11 every mapped table exists | **Yes** | `validate` would fail; V100 must create the missing ones. |
| G12 `workout_profiles` exists | **Yes** | V32 prerequisite. |
| G14 `protein_adaptation_profiles.health_profile_id` unique | **Yes** | The 409 duplicate-insert fix relies on it. |
| G06 `id` is the PK; G15/G16 `gen_random_uuid()` and PG >= 13; G17 NOT VALID constraints | Warning | Decide, but not fatal. |
| G10, G13, G18, G19 | Info | Context for the plan. |

Data results that also **block** adding the corresponding constraint:
- S5.2 `duplicated_ids > 0`.
- S5.3 `orphan_rows > 0`.
- S5.5 `null_rows > 0` for a NOT NULL column (backfill is a data decision).
- S5.6 `unexpected_rows > 0`, which makes Hibernate throw on read.
- S4.6 `TYPE MISMATCH` and `MISSING COLUMN`, which make `validate` fail.

Informational only: S0, S1.9 (except rows in non-JPA legacy tables), S1.11, S2.1-2.3, S3.2-3.4, S4.5, S4.8, S5.1 (except the data-bearing flag), S5.7.

## Drift guide for S4.6/S4.6b

| Status | Effect |
|---|---|
| `MISSING TABLE` / `MISSING COLUMN` | `validate` fails; inserts fail. V100 must add it. |
| `TYPE MISMATCH` | `validate` fails. Known candidates: `LocalDateTime` fields vs `timestamptz`, and the ordinal enum column. |
| `JPA NOT NULL, DB NULLABLE` | `validate` passes. Backfill before adding NOT NULL (S5.5). |
| `DB NOT NULL (no default), JPA NULLABLE` | `validate` passes, but inserts fail when the entity leaves it null. |
| `EXTRA COLUMN` | Informational (legacy). Never dropped by this pack. |

Collection tables: Hibernate creates a PK `(owner_id, value)` only for the NOT NULL value columns
(cuisines, taste preferences, protein sources, religious restrictions). The five nullable ones have no PK by design.
S4.2 reports "ok (no PK expected, none present)" for them.

## Reproducing the local checksums

```
jshell --class-path flyway-core-11.14.1.jar;<slf4j-api;jackson jars>
var r = new FileSystemResource(new Location("filesystem:<abs path to db/migration>"), "<abs path>/V17__convert_health_profile_to_jsonb.sql", StandardCharsets.UTF_8, false);
ChecksumCalculator.calculate(r)
```

Flyway's calculation strips line endings and any BOM. The files use CRLF with no BOM, so the checksum is the same on every checkout.

## Known limits of this pack

- Static checks only: balanced parentheses and quotes, no write keywords, all `@@...@@` placeholders replaced. No PostgreSQL parser was available.
- Where `information_schema` is filtered by privileges, the connected role needs enough rights to see all tables (S0.4 `can_select`).
- Exact counts need `SELECT` on each table. If RLS filters rows, S4/S5 counts are lower bounds.
- The pack reads `public` only. S0.5 lists other schemas that might hold relevant tables.
- It cannot show who changed the schema outside Flyway, or when.
